01 · Platform Model

One platform, four workspaces, one identity

Auriva is entity-centric, not app-centric. Four workspaces are four views over the same shared entities (patients, appointments, prescriptions, queues). A person holds one Auriva ID and may hold multiple roles — a doctor is also a patient; a clinic owner is also a doctor.

PublicMarketplaceAnonymous · SEO-indexed · discovery & acquisition · auriva.in/*
ConsumerPatient WorkspaceMobile-first · role: patient · /app/patient/*
ProfessionalDoctor WorkspaceDesktop-first · role: doctor · /app/doctor/*
BusinessOrganization WorkspaceDesktop · roles: owner/admin/reception/lab/pharmacy · /app/org/{orgId}/*
SHARED PLATFORM CORE — one source of truth
Every workspace is a role-scoped projection of these entities
Auriva ID (auth & roles)Patient RecordAppointmentQueueConsultPrescriptionLab Order / ReportInvoiceNotificationConsent (ABDM)Search
Structural rules
  • Workspace = top-level namespace. A user is always in exactly one workspace; switching happens only via the account menu (top-left), never via inline links.
  • Entities are shared; screens are not. The same appointment appears in three workspaces, each with its own screen, permissions and vocabulary.
  • Navigation depth caps: Marketplace ≤ 3 · Patient ≤ 3 · Doctor ≤ 3 · Organization ≤ 4. Nothing on the platform is ever deeper than 4 levels.
  • Org workspace is multi-branch: {orgId} scopes everything; a branch switcher sits in the org sidebar header.

03 · Module Hierarchy

Module Hierarchy & Parent–Child Relationships

The formal containment model. Level 0 = workspace, Level 1 = module (primary nav), Level 2 = sub-module (secondary nav), Level 3/4 = record detail. A child never appears in navigation without its parent; records are reached only through their owning list.

LevelWhat it isNavigation surfaceExamples
L0 WorkspaceRole-scoped namespaceWorkspace switcher (account menu)Marketplace · Patient · Doctor · Organization
L1 ModuleA job-to-be-done clusterPrimary nav — bottom tabs / sidebar / top barCare · Records · Today · Front Desk · Billing
L2 Sub-moduleA list, board or tool inside a moduleSecondary nav — in-page tabs, sidebar childrenAppointments list · Queue board · Rx Templates
L3 RecordOne entity instanceRow click → page (mobile) or drawer (desktop)Appointment detail · Patient record · Invoice
L4 Sub-recordWork item inside a record (org only)Within-record navigationLab results entry · Dispense detail
Parent–child rules
  • Single parent: every screen has exactly one canonical parent for breadcrumbs and back behaviour, even if it is linked from many places. A prescription's parent is always Records → Prescriptions (patient) or Consult (doctor), never the notification that opened it.
  • Tabs are children, not siblings: tabs inside a record (Overview / Timeline / Reports) are L3 sections of one record, share one URL prefix, and never appear in sidebars.
  • Flows have no children: steppers (booking, walk-in registration, onboarding) are modal journeys that exit back to their launching parent. You cannot deep-link into step 3.
  • Drawers don't change level: a drawer shows an L3 record over its L2 list; the list stays the location. Closing the drawer restores list state (filters, scroll).
  • Cross-links open the target's canonical location in the current workspace — e.g. a lab report referenced in a consult opens under Reports, with back returning to the consult.

05 · Cross-Navigation

Cross-Navigation Rules

How movement between workspaces is allowed, and deliberately constrained. The default is isolation; crossing is explicit and rare.

RuleStatementRationale
X1Workspace switching only via the account menu. No inline link ever silently moves a user between workspaces.A receptionist mid-check-in must never "fall into" their patient account.
X2Marketplace → Patient is the only automatic crossing. Completing a booking or sign-in hands off to /app/patient with the booked appointment in view.Conversion path must be seamless; it is the product's front door.
X3Entity links resolve inside the current workspace's projection. A doctor clicking a patient name gets the clinical record, never the org-admin or patient view.Permissions and vocabulary stay role-appropriate.
X4Public provider profiles are canonical. When a patient views a doctor from an appointment, it opens the marketplace profile (new context), not a private copy.One source of truth for provider identity; SEO benefits.
X5Doctor ↔ Organization share live objects, not navigation. The doctor's queue is a filtered view of the org queue board; neither workspace links into the other's screens.Same data, different jobs. No privilege leakage.
X6Notifications deep-link into the recipient-role's workspace and land on the entity's canonical location.Predictable landing; back button behaves.
X7Back always returns to the originating list with state preserved (filters, scroll, selection) — across drawers, records and flows.Receptionist speed; zero re-orientation cost.

08 · Breadcrumbs

Breadcrumb Strategy

Breadcrumbs reflect the canonical parent chain (§03), never browsing history. Each surface gets exactly the wayfinding it needs — no more.

SurfaceStrategyExample
MarketplaceFull breadcrumbs on all L2+ pages, with BreadcrumbList structured data for SEO. Home is always the anchor.Home / Cardiology / Bangalore / Dr. Arjun Mehta
Patient (mobile)No breadcrumbs. Back button + descriptive page titles. Depth ≤ 3 makes trails redundant; tabs re-anchor instantly.← Prescription · 12 Jun
Doctor (desktop)Breadcrumbs from L3 only (records). L1/L2 are visible in the sidebar, so repeating them is noise. Current page is plain text, not a link.Patients / Ananya Sharma
Organization (desktop)Breadcrumbs from L3, mandatory at L4. Module root is the first crumb; branch context shows in the sidebar, not the trail.Diagnostics / Orders / ORD-4412 · Results
Universal rules
  • Drawers never add a crumb — the underlying list remains the location.
  • Record tabs never appear in the trail (Patients / Ananya Sharma, not … / Timeline).
  • Flows show a stepper, not breadcrumbs; exiting returns to the launching parent.
  • Trails are max 3 links + current page — guaranteed by the depth caps in §01.
09 · Principles

Navigation Principles

Eight rules every future screen must pass before it enters APS-005. These operationalize the APS-002 UX principles at the structural level.

N1

Three clicks to any job

From workspace landing to completing a core action (check-in, prescribe, book, view report) in ≤ 3 interactions. The IA is shaped backwards from this.

N2

Depth is capped, forever

Marketplace/Patient/Doctor ≤ 3 levels, Organization ≤ 4. A new feature that "needs" level 5 is a mis-modelled feature.

N3

One home per workspace

Patient → Home, Doctor → Today, Org → Front Desk, Marketplace → Search. The logo always returns there. Landing views answer "what needs me now?"

N4

Lists own their records

Desktop records open in drawers over their list; the list keeps filters and scroll. Full pages are reserved for workbenches and deep records.

N5

Filters are state, not places

Search, filters and tabs mutate URL state on one screen. We never create "Cancelled Appointments" as a separate IA node.

N6

Role hides, never disables

Navigation shows only what the role can use — a receptionist sees Operate, not a greyed-out Billing. Fewer items beats explained items.

N7

⌘K is the escape hatch

Global search in every workspace, scoped to that workspace's entities. Power users navigate by typing; the tree exists for everyone else.

N8

Structure survives features

New capability lands inside an existing module or extends the shared core — it never adds a fifth workspace or a new top-level pattern without revisiting this document.
