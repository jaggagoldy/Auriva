Phase 1 · Product Blueprint

Technical Summary & Implementation Handoff

Auriva — Healthcare, Simplified is India's Healthcare Operating System connecting Patients, Doctors, Clinics, Hospitals, Diagnostics and Pharmacies. Phase 1 produced the complete product blueprint: seven specification documents that together define what the product is, every screen it contains, how users move through it, and how every interaction behaves. No feature screens have been designed and no application code has been touched — by design. This document is the single entry point for anyone (frontend, backend, or design) starting implementation.

03 · Screen Inventory & Priorities

96 screens across 9 groups: AUTH(7) · MKT(13) · PAT(18) · DOC(14) · ORG(27) · SET(8) · NOT(3) · PRO(3) · SUP(3). Screen IDs are permanent; modals, drawers and flow steps are not screens.

Priority tiers
  • P0 (41 screens) — the launch spine. Nothing ships without all 41.
  • P1 (36) — fast-follow within the first releases.
  • P2 (19) — later expansion (diagnostics depth, pharmacy, analytics).

Critical path (build order for both design and engineering)

Identity / Auth→ Marketplace Search & Booking→ Check-in (Front Desk)→ Live Queue→ Consultation Workbench→ Prescription

This chain is one physical visit end-to-end and touches all four workspaces. It is validated against journeys J1–J5 in APS-004 with zero P0 gaps found.

04 · Contracts for the Backend

APS-008 defines behavior the backend must enforce, not just the UI. These are the items to align with the backend session before Phase 2 screens are coded.

State machines (server-enforced, every transition logged)

EntityHappy pathKey rules
Appointment Requested → Scheduled → Confirmed → Checked-in → In Consultation → Completed Cancelled / No-show / Rescheduled are actor-gated exits with grace windows; patient-visible changes trigger notifications; transitions are append-only.
Queue token Waiting → Called → With Doctor → Done Called → Waiting at most twice, then Skipped; Emergency inserts at position 1 and requires a typed reason; token numbers are never renumbered.

Write strategy & clinical safety

  • Optimistic writes for reversible actions (rename, reorder, preferences) with undo; pessimistic writes for anything clinical or financial (sign prescription, publish results, payments).
  • Signed prescriptions are immutable. Corrections create a superseding prescription linked to the original — never an edit.
  • Allergy conflict is a hard stop in the Rx composer; override requires a typed clinical reason, which is stored.
  • Consent/sharing: minimum scope by default, explicit who/what/why/how-long on every grant, full access log, one-tap revoke.
  • OTP: single component across sign-in / booking / re-auth / step-up; 30s resend cooldown, voice fallback, never a silent lockout.
  • Idempotent submits on all mutating endpoints (double-click / retry safe).
  • Realtime: queue boards and front-desk lists patch rows in place (target <1s propagation); org switching must resolve role + context in <400ms perceived.

05 · Implementation Guidance

Standing constraint: no changes to the existing app UI code (src/) until designs are finalized and approved. When coding starts, this project's Next.js version has breaking changes — read node_modules/next/dist/docs/ before writing any app code (per AGENTS.md).

How a screen gets built (the composition rule)

Pick shell L1–L5
by workspace (APS-007)+ Pick template T1–T8
assigned per screen (APS-005)+ Apply components & tokens
from APS-002+ Wire behaviors
APS-006 nav + APS-008 patterns

No screen invents its own layout, status colors, overlay behavior, or loading pattern. If a screen appears to need something new, the blueprint gets amended first.

Suggested engineering foundation order (pre-screens)

  • 1. Token layer — CSS custom properties / theme config straight from APS-002 §08.
  • 2. Core components — buttons, inputs, chips, table, drawer, dialog, toast, skeleton (APS-002 §04–05).
  • 3. Layout shells — L1–L5 as app-shell components with the z-index scale (content 0 → chrome 100 → drawer 200 → dialog 300 → palette 400 → toast 500).
  • 4. Status & state-machine primitives — status chip components bound to the fixed palettes; client state mirrors of the two machines.
  • 5. Screens — in P0 critical-path order (§03), each composed per the rule above.
